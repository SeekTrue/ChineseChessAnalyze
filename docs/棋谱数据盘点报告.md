# 棋谱数据盘点报告

盘点日期：2026-11-21
盘点方式：只读扫描（每个目录随机抽样 300 个文件，共检查约 900 个文件），未修改任何棋谱文件。

**目录间关系**：三个目录是同一批棋谱按 ID 分段存放的。ID 重叠极少（「副本」与「大师对局」重叠 60 个 ID，其余两两无重叠），抽样内容哈希未见重复棋局。合并后约为一批 14.6 万编号的棋谱，其中约 12.4 万局实际存在。

## 二、文件格式

统一为 UTF-8 编码的纯文本，每局一个 `.txt` 文件，文件名为棋局 ID。结构如下：

```
对局日期: 2010.05.24 13:00      ← 唯一元数据字段

棋局开始
1. 炮二平五 马８进７              ← 回合号. 红方走法 黑方走法
2. 兵三进一 车９平８
3. 马二进三 炮８平９
...
```

- 抽样 900 个文件：**100% 含「对局日期」和「棋局开始」**，无编码问题。
- 日期格式多样：`YYYY.MM.DD`、`YYYY.MM.DD HH:MM`、`YYYY.MM.DD HH:MM-HH:MM`。
- 每局回合数：中位数 34–39，最少 8，最多 153。约 70–80 步一局。

## 三、关键发现：缺少胜负结果

**900 个抽样文件中，没有任何一个包含胜负/结果信息**（检索「红胜/黑胜/和棋/胜负/结果」等关键词均为 0）。文件末尾就是最后一步走法，也没有终局标记。元数据只有「对局日期」一个字段，没有棋手姓名、等级、赛事名称。

对原架构设计的影响：

- 关键度评分公式 `criticality = 0.25·频率 + 0.15·阶段权重 + 0.35·|胜率−0.5| + 0.25·跨局复用度` 中，**胜率项无法计算**，且无法按执红/执黑归一化。
- 无法做「高手专用结构」分析（无棋手等级）。
- 可行的替代路径：
  1. **从走法推断终局**：末步若为将死/困毙可识别，但「认输」无法从棋谱推断。
  2. **改用过程性指标**：以「该结构出现后的对局延续长度」「后续着法质量」等代替胜率作为重要性代理。
  3. **外部补充结果数据**：若能拿到这批 ID 对应的结果表，可按文件名关联。

## 四、走法格式分析

抽样 48,867 步走法，共 1,291 种不同走法串，全部符合规范中文记谱格式，无异常。

| 类别 | 数量 / 占比 | 说明 |
|---|---:|---|
| 常规走法 | 1,072 种 | 如「炮二平五」「马８进７」 |
| 叠子歧义走法 | 219 种，约 1.4% | 如「前炮平一」「后车进二」，需按同线同兵种规则消歧 |
| 红方数字 | 中文数字 | 纵线用「一二三四五六七八九」 |
| 黑方数字 | 全角数字 | 纵线用「１-９」（注意不是半角） |

**解析器要点**：
- 红黑阵营不能靠 `contains(piece_type,'兵')` 判断（黑方「卒」也归兵类）——延续之前代码评估中发现的 bug，必须用棋子值范围（红 1–7 / 黑 8–14）判断。
- 「进/退」的含义按棋子类型不同：车炮兵卒为步数，马士相为到达纵线。
- 黑方全角数字需先归一化为半角。

## 五、结论与建议

1. 数据规模（12.4 万局）远超 MVP 所需的 500 局，**完全够用**，甚至可以只取 5,000–10,000 局做快速验证。
2. 格式高度统一，解析器可以一次写对，批量处理风险低。
3. **最需要你决策的是胜负数据缺失问题**——它决定了关键度评分怎么设计。
4. 建议的最小闭环仍为：`parseNotation.m`（中文记谱→board 矩阵）→ 逐局面生成编码+七状态特征 → 频率统计 → 标签树。
